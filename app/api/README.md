# Dost AI API (Hostinger)

Upload `ai.php`, `app_credential.php`, `archive_store.php`, `romance_safety.php`, and `.htaccess` to `public_html/api/` on `bisque-bear-900175.hostingersite.com`. `ai.php` loads these PHP files from the same directory; uploading `ai.php` alone will fail. Keep the existing `default.php` image-upload endpoint; this API uses a separate URL:

`https://bisque-bear-900175.hostingersite.com/api/ai.php`

The server needs PHP with the cURL extension and outbound HTTPS access.

## Chat content safety

For chat replies, `ai.php` applies a local, conservative text classifier before forwarding conversation messages and again before returning the model response. Romantic content is blocked when either supplied age is missing, invalid, or under 18; sexual content is blocked for all ages. Requests with an under-18 or unusable age do not forward attached images because the text classifier cannot inspect them. Flagged input is not sent to OpenRouter, and flagged model output is replaced before it is returned or archived. Classifier results and flagged text are not added to AI diagnostic logs; ordinary conversation archiving continues under the existing retention policy. The age values remain self-reported and are not independently verified by the proxy.

## System friend catalog

Upload `friends.php` and the complete `system_friends/` directory to `public_html/api/` on Hostinger. Keep `system_friends/.htaccess` in place so profile JSON files and photo files cannot be fetched directly. Add one UTF-8 `.json` file per friend directly inside `public_html/api/system_friends/`; the filename (without `.json`) is its stable catalog ID and must contain only letters, numbers, `_`, or `-`. The catalog endpoint scans this directory on each request, so new profile JSON files appear without changing or redeploying the API.

Each profile must include non-empty `name`, `age`, and `gender`. Optional string fields are `personality`, `interests`, `memories`, `conversationStyle`, `family`, `familyMembers`, `familyActivities`, `financialCondition`, `address`, `height`, `weight`, `facialFeatures`, `bodyFeatures`, `busyReason`, and `timeZoneId`. Optional schedule fields are `busyStartHour` (0–23) and `busyDurationHours` (4–8). The repository's `system_friends/sample-friend.json` shows the format. To add a photo, put a JPEG, PNG, or WebP file (up to 5 MB) in `system_friends/photos/` and set the profile's `photo` field to either its filename (`asha.jpg`) or `photos/asha.jpg`. Leave it empty for an initials avatar.

`GET https://bisque-bear-900175.hostingersite.com/api/friends.php` lists profiles for the app; `GET .../friends.php?id=<catalog-id>` returns one complete profile. The `photo_url` in profile responses points back to the API, which validates and streams the associated image. A user can add up to seven catalog friends, in addition to up to three custom friends. The app stores an individual local copy with a unique ID and caches its photo for offline use; deleting it from the app does not remove the server catalog profile.

## Conversation archive

Every user and assistant chat message is saved as JSON Lines on the server. Each entry records the installation UUID (`installation_id`, lowercase) and the selected model ID; API keys are never included in logs. The app queues events with WorkManager and retries when offline; chat requests also archive their history before reaching OpenRouter and store the assistant response before returning it. Records are organized under `username_ip/friend_name/session_id/YYYY-MM-DD_HH-MM-SS.jsonl`; path labels are sanitized, the IP comes from the server's `REMOTE_ADDR`, and the filename uses the earliest event timestamp in that session (UTC). Each session file is deduplicated by message ID. The same session path is appended once to `_by_install/<installation-uuid>.txt` under the archive root so a later deletion request can find that install without scanning every file. See `deletion-lookup.txt`. The logs are not exposed by an HTTP read endpoint. Existing flat hash-named logs are left in place; they cannot be reliably reorganized because their records do not contain the names needed for the folder structure. Lines written before this change have no `installation_id`.

Chat accepts one compressed JPEG image per message (up to 300 KB from the app). The API saves it in the same session folder as `<message-id>.jpg` (or the detected PNG/WebP extension) and records the relative filename on that JSONL entry. Images are sent to OpenRouter as multimodal data URLs; choose a vision-capable model. The image files are private and are not embedded as base64 in the JSONL log.

Archives are stored outside the web root. The default directory is the sibling of `realpath` of the folder that contains `api/` (the parent of this file's directory), not the raw `DOCUMENT_ROOT` string. Web requests and the CLI cron therefore use the same folder when `public_html` is a symlink, which is the usual Hostinger layout (`~/public_html` → `~/domains/<site>/public_html`). For `/home/ACCOUNT/public_html/api/ai.php` that is `/home/ACCOUNT/dost-private-data/conversation-archive`. For `/home/ACCOUNT/domains/example.com/public_html/api/ai.php` that is `/home/ACCOUNT/domains/example.com/dost-private-data/conversation-archive`. A path is rejected when its `realpath` is inside `realpath` of `DOCUMENT_ROOT` or of the `api/` parent. `.htaccess` is not the control that protects this directory. The API creates it with `0700` directories and `0600` files. PHP's `open_basedir` must include that parent directory, which Hostinger usually does for the account home. If it does not, add the private directory in hPanel, or set `DOST_CONVERSATION_STORAGE_DIR` to another absolute writable path that is not inside `public_html`. A storage path inside the web root is rejected and chat archival returns HTTP 503 instead of writing there.

An older deployment may still have archives in `public_html/log/`. Upload `archive_store.php` and `migrate_conversation_archive.php` with `ai.php`. From SSH, dry-run then apply:

`php /home/ACCOUNT/public_html/api/migrate_conversation_archive.php`

`php /home/ACCOUNT/public_html/api/migrate_conversation_archive.php --apply`

The script merges down to each session directory. If that user folder already exists in the private archive (because someone chatted after the new code was uploaded), it still copies the legacy sessions instead of skipping the whole tree. JSONL lines are appended and deduplicated by `message_id`. A file whose name already exists is moved under a `migrated-N-` name. Symlinks are not followed. The command exits non-zero and prints anything left under `public_html/log` other than `.htaccess`. `app/api/log/.htaccess` remains only as a deny rule for a leftover `public_html/log/` directory. After a zero exit, delete that leftover directory if the only file left is `.htaccess`. Do not point `DOST_CONVERSATION_STORAGE_DIR` at `public_html/log`. `cleanup_logs.php` drops `_by_install` lines whose session directory is gone and deletes an index file that becomes empty, so the index does not outlive the 3,650-day retention.

## Diagnose AI request failures

The API appends server-side request failures to `ai-errors.jsonl` in the same private storage directory as the conversation archives. Each JSON line includes a UTC timestamp and a failure event; provider failures also include the model, whether the server or client key was used, HTTP status, and (when OpenRouter supplies it) its error message/code and provider name. Connection failures include the cURL error and request duration. API keys, prompts, and chat message contents are not written to this diagnostic file. The file is created with `0600` permissions outside the web root. If PHP cannot write this file, it falls back to PHP's configured server error log. Only requests that reach `ai.php` can be logged here; if no corresponding entry appears, check the app's network connection and hosting access/PHP logs.

## Archive retention

Dost's policy retains each server conversation archive for no more than 3,650 days (10 years) after its last activity. Upload `cleanup_logs.php` beside `ai.php` and configure a daily Hostinger cron job to run it with PHP CLI, for example `php /home/ACCOUNT/public_html/api/cleanup_logs.php` (replace the path with the actual Hostinger path). The script is CLI-only, uses the same private directory as the API, removes expired session folders and attached images, and also expires legacy root-level JSONL archives. If `public_html/log/` still exists and is not the active directory, the same 3,650-day pass runs against it so files left there during migration do not skip retention. That pass is not a reason to keep archives on the web. Each run writes `.cleanup-heartbeat.json` (last run time, the private storage path, and deletion counts) inside the private directory; check its `last_run` timestamp periodically to confirm the cron job is still alive. Confirm the cron job runs successfully and configure any hosting-provider backups with a compatible retention period; the script does not purge provider-managed backups. A deletion request for one install is described in `deletion-lookup.txt`. There is still no delete-archive API.

Copy the plain-text contents of `privacy-policy.txt` into a public Google Sites page, publish that page, and link it from the Play Store listing. The Android app does not open the policy itself; the Play listing is the public link. Republish the Google Sites page whenever `privacy-policy.txt` changes. The current text (effective November 12, 2026) describes local friend deletion, the lack of an in-app server-archive delete, 3,650-day server retention, the fact that this version does not enforce a minimum age, the learned facts and session summaries sent with each chat turn, and install-id lookup for archives written after that field is stored. Merge this text after the backup-exclusion and archive-location changes so the backup and install-id sentences match what is deployed. Publish the policy only after the cleanup job is deployed and scheduled. Google Play requires disclosure of the developer's retention and deletion practices but does not prescribe a universal numeric maximum; 3,650 days (10 years) is Dost's chosen cap, not a Google-mandated period. The policy must continue to match the deployed API, cron job, provider practices, and Play Console Data safety declarations.

## Configure the OpenRouter key

Prefer setting the PHP/server environment variable `OPENROUTER_API_KEY`. If Hostinger does not expose environment variables to PHP, copy `config.example.php` to `config.php` on the server only and replace its placeholders. Do not commit or distribute `config.php`. The included `.htaccess` denies direct HTTP access to it.

Requests that would spend the server key must also send `X-Dost-App-Credential`. Generate a random secret of at least 16 characters and set it as `DOST_APP_CREDENTIAL_SECRET` (or `app_credential_secret` in `config.php`). The release build reads that same environment variable, or the Gradle property `DOST_APP_CREDENTIAL_SECRET`, into `BuildConfig.DOST_APP_CREDENTIAL_SECRET`. The default is empty, so the secret is not stored in git. The header value is `v1.<unix seconds>.<hmac-sha256>`, where the HMAC covers `v1`, the timestamp, and the trimmed `X-Dost-Install-ID` (or an empty installation id when that header is absent). The server accepts the timestamp within fifteen minutes. A 401 is retried once by the app using the server's Date header when the device clock is further off. When the secret is configured, a request with no credential, a bad credential, or a stale timestamp is rejected with HTTP 401 and does not call OpenRouter. If the secret is missing or shorter than 16 characters, those requests get HTTP 503 and the server key is still not used.

`X-OpenRouter-Key` still selects the caller's own key. Those requests skip the credential gate because they do not spend the server key, and the key is still not written to the conversation archive or the diagnostic log. Message logging (`operation=log_message`) also does not spend the server key and does not require the credential. Per-IP limits stay in front of both paths: 30 AI requests per minute and 120 log requests per minute.

Already-installed builds do not send `X-Dost-App-Credential`. After this API is deployed with the secret set, those builds cannot spend the server key until users update to a build that contains the matching secret. They can still chat if they enter their own OpenRouter key. To keep old builds on the server key during the rollout, set `DOST_ALLOW_LEGACY_SERVER_KEY=1`. That restores unauthenticated server-key spend. Turn it off once the updated app is out. The credential is an app-held HMAC secret, not Play Integrity. Someone who extracts it from the APK can still call the API. Play Integrity would need a Play Console project, a Google service account on this host, and a client attestation call.

With no `X-OpenRouter-Key` request header, a request that passes the credential gate uses the server key and only permits the app's listed `:free` models. If the app sends a user's own key in that HTTPS header, any syntactically valid OpenRouter `provider/model` ID is accepted and billed to that user's OpenRouter account. The endpoint does not store the custom key. Review usage and rotate the server key if it is exposed.

## Verify after upload

Open the URL in a browser and expect HTTP 405 with a JSON `POST requests only` message. A successful AI request requires a POST JSON body from the app and a valid server-side key.

From a machine with PHP 8.5 or newer CLI, run `php test_api.php` to check that the deployed endpoint returns the expected response. To check another deployment, pass its URL: `php test_api.php https://example.com/api/ai.php`. This smoke test does not send an AI request or require an API key.

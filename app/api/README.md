## Trusted age cohorts and People eligibility

The app first asks for birth month/year on a neutral age screen; under-13 users are blocked locally before account creation. Play Age Signals supplies an age band and can block a shared range below 13, but does not block teens from the app. After Firebase sign-in, `age_cohort.php` validates the submitted month/year, stores it with a server-issued `dostAgeCohort` (`teen` or `adult`) custom claim, and rejects later date changes. A teen cohort becomes adult only when the stored birth month/year reaches 18.

People remains adults-only. When the short-lived eligibility claim is missing or nearly expired, the app requests a Play Integrity Standard token whose request hash binds the Firebase UID, eligibility result, and a fresh random nonce. The Hostinger endpoint verifies the Firebase ID token, asks Google to decode the Integrity token, checks the package, request hash, token age, Play licensing, app recognition, and device integrity, then sets an adult-only server-side Firebase eligibility claim that expires after six hours. Firestore rules require both the adult cohort and this unexpired claim for People reads and writes. The exact Play Age Signals range is not sent to or stored by Dost's server.

Before deploying this endpoint:

1. Link the Google Cloud project to `com.snigtus.dost` in Play Console and enable the Play Integrity API. Enable Identity Toolkit API for the Firebase project as well.
2. Create a dedicated service account and grant only `firebaseauth.users.get` and `firebaseauth.users.update` on the Firebase project. Keep its JSON key outside `public_html` and outside source control.
3. Configure `DOST_FIREBASE_PROJECT_ID`, `DOST_FIREBASE_WEB_API_KEY`, and `DOST_FIREBASE_SERVICE_ACCOUNT_PATH` for PHP, or use the corresponding fields in server-only `config.php`. The project ID must match the service account and Firebase app. Never place the service-account JSON in `config.php`, the repository, or the web root.
4. Upload `age_cohort.php`, `age_eligibility.php`, and `age_eligibility_support.php`; the cohort endpoint writes immutable server-side birth month/year and `dostAgeCohort` claims. Deploy the matching Firestore rules, and run `php.exe test_age_eligibility.php` plus `npm run test:rules` before release.
5. Test using a Play-installed build and a Play license tester. A sideloaded debug build normally cannot satisfy the licensing verdict.

For QA on a debug or sideloaded build, the server can optionally allow specific Firebase UIDs to pass only the app-recognition and licensing checks. Configure `DOST_AGE_ELIGIBILITY_TEST_MODE=true` (or `age_eligibility_test_mode => true` in server-only `config.php`) and set `DOST_AGE_ELIGIBILITY_TEST_UIDS` to a comma-separated list of Firebase UIDs (or `age_eligibility_test_uids` to an array in `config.php`). Test mode defaults off; only the exact value `true` enables it, and an empty UID list allows nobody. When both are enabled, only `UNRECOGNIZED_VERSION` and `UNLICENSED` are accepted in place of `PLAY_RECOGNIZED` and `LICENSED`.

The server still verifies the Firebase ID token and matching UID, calls Google to decode the Play Integrity token, and requires `requestPackageName=com.snigtus.dost`, the bound request hash/nonce, a timestamp within five minutes, and `MEETS_DEVICE_INTEGRITY`. No client flag or debug-build declaration enables this mode. Successful test requests set the same six-hour eligibility claims while preserving other Firebase custom claims. Every Integrity rejection logs only the failed check, whether the tester path was enabled, and a truncated hash of the UID; no tokens or raw payloads are logged. A non-sensitive reason code is returned only to an authenticated allowlisted tester; other callers continue to receive the generic 403 response. Device integrity is deliberately not relaxed.

Play Console also provides [Play Integrity API test responses](https://developer.android.com/google/play/integrity/setup#test) and license testers for exercising verdict combinations on Play-installed builds, such as Internal testing. These test responses do not make a debug-key sideloaded APK reliably `PLAY_RECOGNIZED`, because its signing certificate does not match Play App Signing. Use the server allowlist to test People from a debug APK; use a Play-installed build to verify the real production Integrity path.

The endpoint does not store ID tokens, Integrity tokens, or age ranges. It rate-limits requests by source IP, uses Google's Standard API replay protection, and returns a short-lived claim; the app refreshes its Firebase ID token after the claim is updated. The existing app-held HMAC used for the AI server key is not used as age proof. Do not rely on Firestore access until the API configuration and Play Console linkage are complete.

## People audio and video calls

The Android call feature uses WebRTC for live audio and optional video, Firestore for call offers, answers, media type, and ICE candidates, Firebase Cloud Messaging (FCM) for incoming-call alerts, and this Hostinger API for authenticated call notifications and short-lived TURN credentials. Older call documents without a media type are treated as audio. Video calls require microphone and camera permissions; incoming FCM alerts remain notification-only, and the camera starts only after the user opens the call and grants permission. Calls are unavailable until the endpoints, Firestore rules and TTL policies, and a TURN server are all configured.

Upload `people_call_support.php`, `people_call_push.php`, and `people_call_ice_servers.php` beside the other API files. Keep the service-account JSON and TURN shared secret outside the repository and web root. Configure:

- `DOST_FIREBASE_PROJECT_ID` and `DOST_FIREBASE_WEB_API_KEY` for the same Firebase project used by the app.
- `DOST_CALL_SERVICE_ACCOUNT_PATH` as an absolute path to the dedicated service-account JSON file.
- `DOST_TURN_URLS` as a comma-separated list of `turn:` or `turns:` URLs, for example `turn:turn.example.net:3478?transport=udp,turn:turn.example.net:3478?transport=tcp,turns:turn.example.net:5349`.
- `DOST_TURN_SHARED_SECRET` as the long random secret shared with coturn's `use-auth-secret` configuration. Never put this value in the app or commit it.

Enable the Identity Toolkit API, Cloud Firestore API, and Firebase Cloud Messaging API. Give the service account only the permissions needed to look up Firebase users, read Firestore calls/chats/block records and list call-token devices, delete invalid token documents, and send FCM messages (`firebaseauth.users.get`, `datastore.entities.get`, `datastore.entities.list`, `datastore.entities.delete`, and `cloudmessaging.messages.create`). A project custom role can hold these permissions. Do not put a downloadable service-account key in the web root.

Provision coturn separately with the same shared secret, a TLS certificate for `turns:` endpoints, and firewall access for the configured listener and relay ports. The API issues `timestamp:uid` usernames with HMAC-SHA1 credentials that expire after one hour. Authenticated call users are limited to 10 push requests and 20 TURN-credential requests per minute, per user and endpoint. Follow [FIRESTORE_SETUP.md](../../FIRESTORE_SETUP.md) to deploy the call rules and enable TTL for the `calls`, `callerCandidates`, and `calleeCandidates` collection groups before enabling calling.

Run `php.exe -l` on all three deployed PHP files and `php.exe test_people_call_support.php` from the API directory. Test incoming calls on separate devices with the app backgrounded and notifications allowed. The test does not provision coturn or send an FCM message.

## Chat content safety

For chat replies, `ai.php` applies a local, conservative, keyword-and-phrase text heuristic to the latest user text before forwarding a turn and again before returning the model response. Romantic text is blocked when either supplied age is missing, invalid, or under 18; sexual text is blocked for all ages. The heuristic can miss indirect wording and can flag benign text that matches an ambiguous term; it is not a guarantee of content moderation. It does not inspect image content: requests with an under-18 or unusable age do not forward attached images, but adult image attachments are sent to the selected model provider without image-content moderation. Flagged input is not sent to OpenRouter, and flagged prior turns are omitted from later provider context so one refusal does not persist into subsequent safe turns. Flagged model output is replaced before it is returned or archived, using the selected chat language (English, Bangla, or Hindi). Classifier results and flagged text are not added to AI diagnostic logs; ordinary conversation archiving continues under the existing retention policy. The age values remain self-reported and are not independently verified by the proxy.

## Conversation archive

Every user and assistant chat message is saved as JSON Lines on the server. Each entry records the installation UUID (`installation_id`, lowercase) and the selected model ID; API keys are never included in logs. The app queues events with WorkManager and retries when offline; chat requests also archive their history before reaching OpenRouter and store the assistant response before returning it. Records are organized under `username_ip/friend_name/session_id/YYYY-MM-DD_HH-MM-SS.jsonl`; path labels are sanitized, the IP comes from the server's `REMOTE_ADDR`, and the filename uses the earliest event timestamp in that session (UTC). Each session file is deduplicated by message ID. The same session path is appended once to `_by_install/<installation-uuid>.txt` under the archive root so the app's delete request can find that install without scanning every file. `POST https://bisque-bear-900175.hostingersite.com/api/delete_archive.php` with both `X-Dost-Install-ID` and `X-Dost-App-Credential` deletes the indexed session folders and attached images for that installation and removes its index; repeating the request succeeds with zero sessions deleted. A minimal hashed installation deletion marker remains so delayed events created before deletion are not re-archived; events created afterward can be archived normally. The endpoint does not require a Firebase account, but it does require the time-bound app credential. Existing flat hash-named logs are left in place; they cannot be reliably reorganized because their records do not contain the names needed for the folder structure. Lines written before this change have no `installation_id` and cannot be associated with an installation by the delete API. See `deletion-lookup.txt`.

Chat accepts one compressed JPEG image per message (up to 300 KB from the app). The API saves it in the same session folder as `<message-id>.jpg` (or the detected PNG/WebP extension) and records the relative filename on that JSONL entry. Images are sent to OpenRouter as multimodal data URLs; choose a vision-capable model. The image files are private and are not embedded as base64 in the JSONL log.

Archives are stored outside the web root. The default directory is the sibling of `realpath` of the folder that contains `api/` (the parent of this file's directory), not the raw `DOCUMENT_ROOT` string. Web requests and the CLI cron therefore use the same folder when `public_html` is a symlink, which is the usual Hostinger layout (`~/public_html` → `~/domains/<site>/public_html`). For `/home/ACCOUNT/public_html/api/ai.php` that is `/home/ACCOUNT/dost-private-data/conversation-archive`. For `/home/ACCOUNT/domains/example.com/public_html/api/ai.php` that is `/home/ACCOUNT/domains/example.com/dost-private-data/conversation-archive`. A path is rejected when its `realpath` is inside `realpath` of `DOCUMENT_ROOT` or of the `api/` parent. `.htaccess` is not the control that protects this directory. The API creates it with `0700` directories and `0600` files. PHP's `open_basedir` must include that parent directory, which Hostinger usually does for the account home. If it does not, add the private directory in hPanel, or set `DOST_CONVERSATION_STORAGE_DIR` to another absolute writable path that is not inside `public_html`. A storage path inside the web root is rejected and chat archival returns HTTP 503 instead of writing there.

An older deployment may still have archives in `public_html/log/`. Upload `archive_store.php` and `migrate_conversation_archive.php` with `ai.php`. From SSH, dry-run then apply:

`php /home/ACCOUNT/public_html/api/migrate_conversation_archive.php`

`php /home/ACCOUNT/public_html/api/migrate_conversation_archive.php --apply`

The script merges down to each session directory. If that user folder already exists in the private archive (because someone chatted after the new code was uploaded), it still copies the legacy sessions instead of skipping the whole tree. JSONL lines are appended and deduplicated by `message_id`. A file whose name already exists is moved under a `migrated-N-` name. Symlinks are not followed. The command exits non-zero and prints anything left under `public_html/log` other than `.htaccess`. `app/api/log/.htaccess` remains only as a deny rule for a leftover `public_html/log/` directory. After a zero exit, delete that leftover directory if the only file left is `.htaccess`. Do not point `DOST_CONVERSATION_STORAGE_DIR` at `public_html/log`. `cleanup_logs.php` drops `_by_install` lines whose session directory is gone and deletes an index file that becomes empty, so the index does not outlive the 1,095-day retention.

## Diagnose AI request failures

The API appends server-side request failures to `ai-errors.jsonl` in the same private storage directory as the conversation archives. Each JSON line includes a UTC timestamp and a failure event; provider failures also include the model, whether the server or client key was used, HTTP status, and (when OpenRouter supplies it) its error message/code and provider name. Connection failures include the cURL error and request duration. API keys, prompts, and chat message contents are not written to this diagnostic file. The file is created with `0600` permissions outside the web root. If PHP cannot write this file, it falls back to PHP's configured server error log. Only requests that reach `ai.php` can be logged here; if no corresponding entry appears, check the app's network connection and hosting access/PHP logs.

## Archive retention

Dost's policy retains each server conversation archive for no more than 1,095 days (three years) after its last activity. Upload `cleanup_logs.php` beside `ai.php` and configure a daily Hostinger cron job to run it with PHP CLI, for example `php /home/ACCOUNT/public_html/api/cleanup_logs.php` (replace the path with the actual Hostinger path). Upload `telemetry_store.php` with it; the script also removes anonymous daily telemetry aggregates older than 90 days. The script is CLI-only, uses the same private directory as the API, removes expired session folders and attached images, and also expires legacy root-level JSONL archives. If `public_html/log/` still exists and is not the active directory, the same 1,095-day pass runs against it so files left there during migration do not skip retention. That pass is not a reason to keep archives on the web. Each run writes `.cleanup-heartbeat.json` (last run time, the private storage path, and deletion counts) inside the private directory; check its `last_run` timestamp periodically to confirm the cron job is still alive. Confirm the cron job runs successfully and configure any hosting-provider backups with a compatible retention period; the script does not purge provider-managed backups. The in-app archive deletion request is described in `deletion-lookup.txt`.

Copy the reviewed plain-text contents of `privacy-policy.txt` into a public Google Sites page, publish that page, and link it from the Play Store listing. Settings → Privacy also links to the published policy. Republish the page whenever the policy changes. Before release, reconcile the policy with the deployed API, age and mode implementations, cron job, provider practices, and Play Console Data safety declarations. Google Play does not prescribe a universal numeric retention maximum; the stated 1,095-day archive period is Dost's chosen cap.

## Configure the OpenRouter key

Prefer setting the PHP/server environment variable `OPENROUTER_API_KEY`. If Hostinger does not expose environment variables to PHP, copy `config.example.php` to `config.php` on the server only and replace its placeholders. Do not commit or distribute `config.php`. The included `.htaccess` denies direct HTTP access to it.

Server-key completion requests and both archive endpoints require `X-Dost-App-Credential`. Generate a random secret of at least 16 characters and set it as `DOST_APP_CREDENTIAL_SECRET` (or `app_credential_secret` in `config.php`). The release build reads that same environment variable, or the Gradle property `DOST_APP_CREDENTIAL_SECRET`, into `BuildConfig.DOST_APP_CREDENTIAL_SECRET`. The default is empty, so the secret is not stored in git. The header value is `v1.<unix seconds>.<hmac-sha256>`, where the HMAC covers `v1`, the timestamp, and the trimmed `X-Dost-Install-ID` (or an empty installation id when that header is absent). The server accepts the timestamp within fifteen minutes. A 401 is retried once by the app using the server's Date header when the device clock is further off. When the secret is configured, a request with no credential, a bad credential, or a stale timestamp is rejected with HTTP 401. If the secret is missing or shorter than 16 characters, those requests get HTTP 503. This secret is included in the client build and is only a basic gate; it is not strong authentication against a determined client.

`X-OpenRouter-Key` still selects the caller's own key. Completion requests using that key skip the server-key credential gate because they do not spend the server key, and the key is still not written to the conversation archive or the diagnostic log. Message logging (`operation=log_message`) does not spend the server key but does require the credential; archive deletion also requires it. Per-IP limits stay in front of AI and log paths: 30 AI requests per minute and 120 log requests per minute.

Already-installed builds do not send `X-Dost-App-Credential`. After this API is deployed with the secret set, those builds cannot spend the server key until users update to a build that contains the matching secret. They can still chat if they enter their own OpenRouter key. To keep old builds on the server key during the rollout, set `DOST_ALLOW_LEGACY_SERVER_KEY=1`. That restores unauthenticated server-key spend. Turn it off once the updated app is out. The credential is an app-held HMAC secret, not Play Integrity. Someone who extracts it from the APK can still call the API.

With no `X-OpenRouter-Key` request header, a request that passes the credential gate uses the server key and only permits the app's listed `:free` models. If the app sends a user's own key in that HTTPS header, any syntactically valid OpenRouter `provider/model` ID is accepted and billed to that user's OpenRouter account. The endpoint does not store the custom key. Review usage and rotate the server key if it is exposed.

## Verify after upload

Open the URL in a browser and expect HTTP 405 with a JSON `POST requests only` message. A successful AI request requires a POST JSON body from the app and a valid server-side key.

From a machine with PHP 8.5 or newer CLI, run `php test_api.php` to check that the deployed endpoint returns the expected response. To check another deployment, pass its URL: `php test_api.php https://example.com/api/ai.php`. This smoke test does not send an AI request or require an API key.
